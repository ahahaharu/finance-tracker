# Техническое задание

**Проект:** finance-tracker — система учёта личных финансов
**Версия документа:** 1.0
**Статус:** утверждено к разработке

---

## 1. Общие сведения

### 1.1. Назначение

Веб-приложение для учёта личных доходов и расходов. Пользователь ведёт несколько
счетов в разных валютах, регистрирует операции, распределяет их по категориям,
задаёт лимиты расходов и получает сводную аналитику в единой валюте отчётности.

### 1.2. Цель разработки

Создать работоспособную систему, демонстрирующую полный цикл: проектирование
базы данных, реализацию серверной бизнес-логики, REST API, веб-интерфейс,
разграничение доступа по ролям, автоматизированное тестирование и развёртывание.

### 1.3. Границы системы

Система работает как самостоятельное веб-приложение. Интеграции с банковскими
системами, платёжными сервисами и мобильными приложениями не предусмотрены.
Единственный внешний источник данных — открытый API Национального банка
Республики Беларусь для получения курсов валют.

## 2. Анализ предметной области

### 2.1. Постановка проблемы

Человек, ведущий личный бюджет, сталкивается с четырьмя задачами:

1. **Фиксация операций.** Деньги хранятся в нескольких местах: наличные, карта,
   накопительный счёт. Без единой точки учёта фактический остаток неизвестен.
2. **Классификация.** Без разбиения расходов по категориям сумма трат ничего
   не говорит о том, на что именно уходят деньги.
3. **Контроль.** Ограничение расходов работает только тогда, когда лимит задан
   заранее и текущее исполнение видно в любой момент, а не по итогам месяца.
4. **Мультивалютность.** При наличии счетов в разных валютах общий остаток
   невозможно получить простым суммированием — требуется приведение к единой
   валюте по корректному курсу.

### 2.2. Обзор аналогов

| Продукт | Сильные стороны | Ограничения |
|---|---|---|
| CoinKeeper | наглядная визуализация, быстрый ввод операций | ключевые функции в платной подписке, слабый веб-клиент |
| YNAB | продуманная методология планирования бюджета | высокий порог входа, платный, нет русской локализации |
| Money Manager | простота, работа офлайн | только мобильное приложение, слабая аналитика |
| Zen-money | автоматический импорт из банков | зависимость от поддержки конкретных банков, закрытые данные |

### 2.3. Выводы для проектирования

1. Ввод операции должен занимать минимум действий — это самый частый сценарий.
2. Мультивалютность необходима, но конвертация должна выполняться по курсу
   **на дату операции**, а не по текущему: расход, совершённый в марте,
   не изменяется от колебаний курса в августе.
3. Контроль бюджета имеет смысл только при отображении текущего исполнения
   в момент ввода операции.
4. Интерфейс — плотный табличный, ориентированный на просмотр большого числа
   записей, а не на демонстрационную визуализацию.

## 3. Пользователи и роли

### 3.1. USER — владелец бюджета

Основной пользователь. Ведёт собственные счета, категории, операции и бюджеты.
Не имеет доступа к данным других пользователей ни через интерфейс, ни через API.

### 3.2. ADMIN — администратор системы

Обслуживает систему: просматривает список учётных записей, блокирует и
разблокирует их, изменяет роли, просматривает агрегированную статистику
использования, инициирует обновление курсов валют.

Администратор **не имеет доступа к содержимому финансовых данных**
пользователей: суммы, операции, категории и бюджеты ему недоступны.
Доступны только агрегаты по системе в целом и метаданные учётных записей.
Это осознанное проектное решение, а не упущение.

## 4. Пользовательские сценарии

**С-1. Регистрация и начало работы.**
Пользователь регистрируется, указывает валюту отчётности. Система создаёт
для него набор категорий по умолчанию. Пользователь заводит первый счёт
с начальным остатком.

**С-2. Регистрация расхода.**
Пользователь открывает форму быстрого ввода, указывает сумму, счёт, категорию
и дату. Система сохраняет операцию, пересчитывает остаток счёта и, если для
категории задан бюджет, показывает актуальное исполнение лимита.

**С-3. Просмотр и поиск операций.**
Пользователь открывает список операций, фильтрует по периоду, счёту, категории
и типу, находит нужную запись, исправляет сумму. Параметры фильтра сохраняются
в адресной строке и доступны для повторного открытия.

**С-4. Перевод между счетами.**
Пользователь переводит средства с карточного счёта на накопительный.
При различии валют он указывает списанную и зачисленную суммы; система выводит
фактический курс операции и сохраняет обе записи как единое целое.

**С-5. Планирование бюджета.**
Пользователь задаёт месячный лимит по категории. В течение месяца видит
на дашборде долю израсходованного лимита и получает визуальное предупреждение
при его превышении.

**С-6. Анализ расходов за период.**
Пользователь открывает дашборд, выбирает период и получает суммы дохода,
расхода и сальдо в валюте отчётности, а также распределение расходов
по категориям.

**С-7. Администрирование.**
Администратор открывает панель управления, находит учётную запись,
просматривает дату регистрации и активность, при необходимости блокирует её.

## 5. Функциональные требования

### 5.1. Аутентификация и учётные записи

| № | Требование |
|---|---|
| FR-1.1 | Регистрация по адресу электронной почты и паролю. Адрес уникален в системе. |
| FR-1.2 | Пароль хранится только в виде хеша (bcrypt, cost ≥ 10). |
| FR-1.3 | Пароль при регистрации: не менее 8 символов, содержит букву и цифру. |
| FR-1.4 | Вход по паре «адрес — пароль». Сессия на основе JWT, срок жизни 30 суток. |
| FR-1.5 | Выход из системы с аннулированием сессии. |
| FR-1.6 | Пользователь редактирует имя и валюту отчётности в настройках профиля. |
| FR-1.7 | Смена пароля с подтверждением текущего. |
| FR-1.8 | Заблокированная учётная запись не может войти в систему; активная сессия прекращается при первом запросе. |
| FR-1.9 | При регистрации создаётся набор категорий по умолчанию (не менее 8 расходных и 3 доходных). |

### 5.2. Счета

| № | Требование |
|---|---|
| FR-2.1 | Создание счёта: наименование, тип (`CASH`, `CARD`, `SAVINGS`), валюта, начальный остаток. |
| FR-2.2 | Валюта счёта задаётся при создании и в дальнейшем не изменяется. |
| FR-2.3 | Редактирование наименования, типа и начального остатка. |
| FR-2.4 | Удаление счёта. Счёт, по которому есть операции, удалить нельзя — система возвращает ошибку с указанием количества связанных записей. |
| FR-2.5 | Текущий остаток счёта вычисляется как начальный остаток плюс сумма всех операций по нему. Денормализованное хранение остатка не применяется. |
| FR-2.6 | Список счетов с остатками в собственной валюте и в валюте отчётности. |
| FR-2.7 | Наименование счёта уникально в пределах учётной записи. |

### 5.3. Категории

| № | Требование |
|---|---|
| FR-3.1 | Создание категории: наименование, вид (`INCOME` или `EXPENSE`), цвет. |
| FR-3.2 | Категории вида `INCOME` доступны только для операций дохода, `EXPENSE` — только для расхода. |
| FR-3.3 | Редактирование наименования и цвета. Вид категории после создания не изменяется. |
| FR-3.4 | Удаление категории. Категория со связанными операциями не удаляется. |
| FR-3.5 | Наименование категории уникально в пределах учётной записи и вида. |
| FR-3.6 | Иерархия категорий не поддерживается — структура плоская. |

### 5.4. Операции

| № | Требование |
|---|---|
| FR-4.1 | Создание операции: тип (`INCOME`, `EXPENSE`), сумма, счёт, категория, дата, необязательный комментарий. |
| FR-4.2 | Сумма строго больше нуля. Знак операции определяется её типом, а не знаком суммы. |
| FR-4.3 | Суммы хранятся целым числом в минорных единицах валюты. Тип с плавающей точкой для денежных величин не применяется. |
| FR-4.4 | Дата операции не может быть в будущем. |
| FR-4.5 | Категория операции соответствует её типу (см. FR-3.2). |
| FR-4.6 | При сохранении фиксируется курс валюты счёта к валюте отчётности на дату операции; сумма в валюте отчётности сохраняется вместе с операцией. |
| FR-4.7 | Редактирование операции. При изменении суммы, даты или счёта сумма в валюте отчётности пересчитывается. |
| FR-4.8 | Удаление операции. |
| FR-4.9 | Комментарий — не более 500 символов. |

### 5.5. Переводы между счетами

| № | Требование |
|---|---|
| FR-5.1 | Перевод создаёт две связанные записи — списание и зачисление — объединённые общим идентификатором группы. |
| FR-5.2 | Обе записи создаются в рамках одной транзакции базы данных: частичное сохранение недопустимо. |
| FR-5.3 | При совпадении валют счетов указывается одна сумма. |
| FR-5.4 | При различии валют пользователь указывает списанную и зачисленную суммы; фактический курс операции вычисляется как их отношение и сохраняется. |
| FR-5.5 | Счёт-источник и счёт-получатель не совпадают. |
| FR-5.6 | Перевод не относится ни к одной категории и не учитывается в статистике доходов и расходов. |
| FR-5.7 | Удаление перевода удаляет обе записи группы. |
| FR-5.8 | Редактирование перевода выполняется как удаление и создание заново. |

### 5.6. Бюджеты

| № | Требование |
|---|---|
| FR-6.1 | Создание бюджета: категория вида `EXPENSE`, сумма лимита, период (календарный месяц). |
| FR-6.2 | Для одной категории в одном периоде существует не более одного бюджета. |
| FR-6.3 | Исполнение бюджета вычисляется как сумма расходов по категории за период в валюте отчётности. |
| FR-6.4 | Отображается сумма лимита, израсходованная сумма, остаток и доля исполнения в процентах. |
| FR-6.5 | При превышении лимита бюджет отмечается визуально. |
| FR-6.6 | Редактирование суммы лимита и удаление бюджета. |
| FR-6.7 | Автоматический перенос бюджета на следующий период не выполняется. |

### 5.7. Валюты и курсы

| № | Требование |
|---|---|
| FR-7.1 | Поддерживаются валюты BYN, USD, EUR. |
| FR-7.2 | Валюта отчётности задаётся в профиле; по умолчанию BYN. |
| FR-7.3 | Курсы загружаются из открытого API Национального банка Республики Беларусь и сохраняются в базе данных. |
| FR-7.4 | Курс хранится с привязкой к дате, паре валют и значению. |
| FR-7.5 | При отсутствии курса на требуемую дату применяется ближайший предшествующий. При отсутствии предшествующего курса операция отклоняется с явной ошибкой. |
| FR-7.6 | Пересчёт исторических операций по текущему курсу не выполняется. |
| FR-7.7 | При смене валюты отчётности суммы в валюте отчётности пересчитываются по курсам соответствующих дат. |
| FR-7.8 | Округление при конвертации — до минорной единицы, метод «половина вверх». |

Уточнение к FR-7.6: запрет на пересчёт по текущему курсу относится
к историческим операциям и к итогам за период. Текущий остаток счёта историей
не является и конвертируется в валюту отчётности по курсу на текущую дату
(`docs/data-model.md`, §5.8).

### 5.8. Аналитика

| № | Требование |
|---|---|
| FR-8.1 | Общий остаток по всем счетам в валюте отчётности. |
| FR-8.2 | Суммы дохода, расхода и сальдо за выбранный период. |
| FR-8.3 | Распределение расходов по категориям за период с указанием доли каждой категории. |
| FR-8.4 | Динамика расходов по месяцам за последние 6 месяцев. |
| FR-8.5 | Список последних операций на дашборде. |
| FR-8.6 | Переводы исключаются из всех расчётов доходов и расходов. |

### 5.9. Фильтрация и списки

| № | Требование |
|---|---|
| FR-9.1 | Фильтрация операций по периоду, счёту, категории и типу. |
| FR-9.2 | Текстовый поиск по комментарию. |
| FR-9.3 | Постраничный вывод, 50 записей на страницу. |
| FR-9.4 | Сортировка по дате, по умолчанию — от новых к старым. |
| FR-9.5 | Параметры фильтрации отражаются в адресной строке и восстанавливаются при повторном открытии. |
| FR-9.6 | Отображение итоговой суммы по текущему набору фильтров. |
| FR-9.7 | Выгрузка отфильтрованного списка операций в формате CSV. |

### 5.10. Администрирование

| № | Требование |
|---|---|
| FR-10.1 | Список учётных записей: адрес, имя, роль, дата регистрации, статус, количество операций. |
| FR-10.2 | Блокировка и разблокировка учётной записи. |
| FR-10.3 | Изменение роли учётной записи. |
| FR-10.4 | Администратор не может изменить роль или заблокировать собственную учётную запись. |
| FR-10.5 | Агрегированная статистика: число учётных записей, число операций, распределение регистраций по датам. |
| FR-10.6 | Принудительное обновление курсов валют. |
| FR-10.7 | Финансовые данные пользователей администратору недоступны. |

### 5.11. REST API

| № | Требование |
|---|---|
| FR-11.1 | Операции создания, чтения, изменения и удаления доступны через REST API с префиксом `/api/v1`. |
| FR-11.2 | Аутентификация запросов — по сессионному cookie. |
| FR-11.3 | Единый формат ошибки: `{ error: { code, message, details? } }`. |
| FR-11.4 | Коды состояния: 200, 201, 400 (некорректный запрос), 401 (не аутентифицирован), 403 (нет прав), 404 (не найдено), 409 (конфликт), 422 (ошибка валидации). |
| FR-11.5 | Ответ с ошибкой содержит машиночитаемый код; текст сообщения формируется на стороне клиента согласно выбранной локали. |
| FR-11.6 | Постраничный вывод и фильтрация — по единым правилам для всех коллекций. |
| FR-11.7 | Спецификация API публикуется в формате OpenAPI и доступна в интерфейсе. |

## 6. Нефункциональные требования

### 6.1. Безопасность

| № | Требование |
|---|---|
| NFR-1.1 | Проверка принадлежности запрашиваемого ресурса текущему пользователю выполняется в сервисном слое, независимо от проверок в интерфейсе и промежуточном слое маршрутизации. |
| NFR-1.2 | Проверка роли для операций администрирования выполняется в сервисном слое. |
| NFR-1.3 | Все входные данные проверяются схемой на стороне сервера; проверка на стороне клиента носит вспомогательный характер. |
| NFR-1.4 | Пароли не выводятся в журналы и не возвращаются в ответах API. |
| NFR-1.5 | Ограничение частоты запросов к точкам входа регистрации и аутентификации — не более 10 попыток за 15 минут с одного адреса. |
| NFR-1.6 | Секреты хранятся в переменных окружения и не попадают в систему контроля версий. |

### 6.2. Корректность данных

| № | Требование |
|---|---|
| NFR-2.1 | Операции, изменяющие более одной записи, выполняются в транзакции базы данных. |
| NFR-2.2 | Ссылочная целостность обеспечивается ограничениями на уровне базы данных, а не только на уровне приложения. |
| NFR-2.3 | Денежные величины не подвергаются вычислениям с плавающей точкой ни на одном этапе. |

### 6.3. Интерфейс

| № | Требование |
|---|---|
| NFR-3.1 | Локализация интерфейса: русский и английский языки, переключение без перезагрузки данных. |
| NFR-3.2 | Оформление соответствует документу `docs/design-system.md`. |
| NFR-3.3 | Работоспособность при ширине окна от 1024 пикселей; при меньшей ширине допускается упрощённая компоновка. |
| NFR-3.4 | Для каждого списка предусмотрены состояния: загрузка, пустой список, ошибка. |
| NFR-3.5 | Светлая и тёмная темы оформления. |

### 6.4. Качество и сопровождение

| № | Требование |
|---|---|
| NFR-4.1 | Бизнес-логика сосредоточена в сервисном слое; обработчики маршрутов и серверные действия логики не содержат. |
| NFR-4.2 | Обращение к базе данных выполняется только из слоя доступа к данным. |

## 7. Ограничения и допущения

1. Число пользователей системы не превышает нескольких десятков; требования
   к горизонтальному масштабированию не предъявляются.
2. Число операций у одного пользователя не превышает нескольких тысяч;
   агрегаты вычисляются запросами к базе данных без предварительного расчёта.
3. Курсы валют публикуются внешним источником один раз в сутки; более частое
   обновление не требуется.
4. Все даты и время хранятся в UTC; отображение выполняется в часовом поясе
   клиента.
5. Одновременное редактирование одних и тех же данных из нескольких сессий
   не рассматривается.

## 9. Глоссарий

**Счёт** — место хранения средств: наличные, карта, накопительный счёт.
Имеет собственную валюту, изменяемую только при создании.

**Операция** — единичное движение средств по счёту: доход или расход.

**Перевод** — пара связанных операций: списание с одного счёта и зачисление
на другой. Не относится к доходам или расходам.

**Категория** — классификатор операций. Относится к доходам либо к расходам.

**Бюджет** — ограничение суммы расходов по категории в пределах календарного
месяца.

**Валюта отчётности** — валюта, в которой пользователю показываются сводные
показатели. Задаётся в профиле.

**Курс на дату операции** — значение курса, зафиксированное в момент создания
операции и не изменяющееся впоследствии.

**Минорная единица** — наименьшая денежная единица валюты: копейка для BYN,
цент для USD и EUR.
